# Guided plan and report

## Sub-features

- Clean install: `npm pack` of the checkout, `npm install` in an empty folder, and only the installed `sign-off-axi` posts, serves and answers. No Firstmate, no repo checkout on the path.
- Authoring: `report init <folder>` and `report init <folder> --plan` write a report 4 / plan 3 with required filer to fill (older report 2/3 and plan 1/2 still load); posting one with its `FILL:` lines is refused. The skill (`skills/sign-off-axi/SKILL.md`) names the same commands the installed CLI lists.
- Research bar: the packaged skill tells the author how a research report and a plan clear it (the whole field and a reason for each cut, one item per short-listed option on the same axes, a link on each outside claim, Checked apart from Reported, a pick and a runner-up; a plan adds scope, steps, risks and how done is proven).
- One scroll "Guide" view for a plan (`#waiting/<key>`) and a report (`#reports/<key>`): what this is, what I understood, what I found, what I recommend, what you decide, next step. A desk has the rail, Your answers and Go ahead; a phone has the progress bar and the sticky Go ahead bar.
- Numbers behind a Details tap, one visual per point (bars pair, steps or tiles), items that expand in place, each decision with My pick, Why my pick and If you stay quiet.
- Item detail and comparison tables: an item's `more` keeps its line breaks, one line per point. A section whose items all have `more` with the same `Axis: value` lines in the same order is drawn as one comparison table (options across and axes down at 1280; each axis listing every option under it at 390, and past 4 options). An item with no `more` keeps its buttons inside its own padding.
- Markdown in authored text: every authored field of a plan and report (headings, lead, understood lines, item titles and details, outcomes, next steps, table cells) renders inline `code`, **bold**, *em*, short links (`repo #12`, `HN 123`, the domain), and an item detail's bullet and numbered lists and fenced code. Reading text is 16 px at 1.6 line height, a part heading 20 px (22 px from 700 px wide), the comparison table 16 px stacked at 390 and 13 px with a tinted header once options run across. The raw marks stay in the page hidden, so a selection's code-point offsets still count the raw field; text is escaped and only http(s) links are made, so authored text never becomes raw HTML (`node --test test/markdown.test.mjs`). Drive it with the table-shots journey below plus an item whose `more` holds a list and a fenced block, and read the computed sizes in the page (`getComputedStyle` of the lead, an item paragraph, a table cell) at 390 and 1280, light and dark.
- A capture's tap and the comparison table at 390: on a phone a capture link stays on the board (a report or plan opens its live page, any other card its own screen); on a desk it opens the raw file in a tab. The stacked table reads at 16 px. `PHONE_PART=link|table done-done run phone-capture` (`phone-link-shots.sh`) drives one part per run on a throwaway board and saves `link.<width>.png` or `table.<width>.png` with `measures.txt` (href and new-tab flag; layout, cell font px, columns, options per point, sideways overflow). `node --test --test-name-pattern='capture opens the raw|item detail keeps its line' test/design.test.mjs` is the page-level check.
- Read receipts per part, real: a part on screen for a moment is saved on the board (`POST /api/reads`, `<board>.reads.jsonl`) and shows "Read by you" with the time; "Agent wrote this" shows the filed time; after Go ahead the agent's `wait` takes the answer and the receipt shows "Agent read your answers".
- Go deeper per part, real: the tap is an ask (`POST /api/deeper`, `<board>.deeper.jsonl`) the agent gets from `wait --filer` and answers with `deeper <board> --id <id> --text … [--more]`; the answer streams into that spot with "Agent replied" and a follow-up box.
- Every ask answers the tap (Ask a question's Send, Go deeper, Simplify this, Show an example, Why?, a follow-up, a selected-text preset and a legacy Go deeper): the control turns ink at once and stays so until the board has the ask; the ask then shows under the part, scrolled on screen, as **Sent to the agent** with the time, then **Agent got it** with the time once the agent's wait takes it, **Agent is answering** while it streams, and **Agent replied** with the time; the same ask again (same part, action, words and selection) saves nothing and shows **Already sent** with the first one's time. `node .agents/skills/done-done-verify-sign-off/ask-feedback-shots.mjs <out> light|dark` (journey `ask-feedback`) holds the board's answer back to capture `ask-pressed`, then `ask-sent`, `ask-again` (one ask saved) and `ask-replied` at 390 with a `.txt` of the head, whether it is on screen, the Ask control's state and fill; it also captures `diagram` (a design report whose first picture is the inline-SVG flow in `diagram-sample/flow.html`, at the column's full width) and `diagram-picked` (the board's own light-or-dark pick set against the system's: the drawing follows the pick). The regression is `node --test --test-name-pattern='an ask on a guided report answers the tap' test/design.test.mjs`.
- Go deeper on an answers-only board (a fed board, the live one): the tap is accepted like on any board, no "takes answers only" refusal and no error under the part. `node .agents/skills/done-done-verify-sign-off/fed-deeper-shots.mjs <out> light|dark` posts a report, marks the board `answers_only`, taps Go deeper on its first part at 390 and 1280, and saves `deeper-ask.<width>w.png` plus `.txt` (asks saved before and after, errors shown, overflow). The server side runs in `node --test --test-name-pattern='answers-only board takes Go deeper' test/contract.test.mjs`.
- Not quite with a note on a report, on an answers-only board (the live one): Not quite, a typed note and **Tell the agent** are taken, no "takes answers only" refusal; the note is the `understood` part's Disagree (`POST /api/annotations`), shows under the part with its feedback track at **Sent** (see [Feedback trail](feedback-trail.md)), reaches the report's author as one `comment` event on `wait --filer <id> --events`, then the track reaches **Read** and the receipt says **Agent read your note**; **That is right** is the part's Agree. `node .agents/skills/done-done-verify-sign-off/not-quite-shots.mjs <out> light|dark` (journey `not-quite`) drives it at 390 and saves `not-quite-read` (the end state) with a `.txt` of what the card says, the errors shown, the saved line and the wait event; `NOT_QUITE_STEPS=<folder>` also saves the earlier `not-quite-note` and `not-quite-sent` outside the run folder, and `NOT_QUITE_BEFORE=1 SIGN_OFF_REPO=<built base checkout>` the base's `not-quite-refused`. The regression is `node --test --test-name-pattern='Not quite with a note' test/design.test.mjs`.
- Selected text, real: a native selection inside one authored field (heading, body, understood line, item detail, decision text, next step) shows a tray in the page flow under that field with the same five presets; Ask a question opens its composer in the tray. The request keeps the field, code-point start/end and exact quote (`POST /api/engagement` `selection`), and the quote shows with the pending request and its reply in the part. Collapsing the selection or Escape cancels; a selection across fields or parts offers nothing and saves nothing; copying and the native handles are left alone.
- Diagrams (`diagram` on a plan's or report's visual, section or item): an Archify page, 1 to 3 views as tabs, in a sandboxed frame. Post refuses a page with text under 12 px at 390 (drawing as wide as Full size draws it, 374 px), brand marks, no drawing, or outside the board folder. A diagram page draws in the board's light or dark, not only the system's: the board asks for it with `?theme=` from its own pick and `web/diagram-page.js` turns the page's `prefers-color-scheme` rules on or off with it. On a phone the drawing takes the column's full width with no well around it. On a desk Show me opens the interactive viewer in place and Back to the picture returns the frame to its size; on a phone Show me is hidden (its toolbar is wider than the card) and Full size opens the drawing alone at the screen's width, sized to the drawing with the drawing's own surface below it and a Back to the plan link above it (also on a desk's Full size). Post pins each page with `sha256` and `bytes` like media: a page changed after posting answers 404 and the plan's revision covers its content. `DIAGRAM_DIR=<folder of slices.html, today.html, after.html> node .agents/skills/done-done-verify-sign-off/diagram-shots.mjs <out> light|dark 390|1280` posts a plan with a section diagram and an item with two tabs, drives them, measures the smallest drawn text in Full size at 390 (at least 12 px), that the page ends at the drawing at 390, that Back to the plan is at least 44 px tall and a click on it returns the tab to the plan, and that the same page changed after posting is refused (404) and served again once restored (`pin.*.txt`), and saves plan, section, diagram, item, tab, open (1280) and fullsize shots; `DIAGRAM_BEFORE=1 SIGN_OFF_REPO=<built base checkout>` posts the same plan with no diagram for the before. The pages come from the separately installed archify skill (`architecture`, `viewBox` 320 to 340 wide, `"legend": {"mode": "hidden"}`, `ARCHIFY_UPDATE_CHECK_DISABLED=1 archify finalize --quality showcase`); sign-off ships none. The post-time rules run in `node --test test/diagram.test.mjs`.
- Agree, Disagree and Comment on every part and item, and one Ask menu per part: a part ends with a hairline and one row, Agree, Disagree, Comment, then Details and Ask (Ask a question, Go deeper, Simplify this, Show an example, Why?); every control draws 32 px tall and is a 44 px tap target. Never two rows stacked: every item keeps its one row in its card, and a section's own row shows once at its end, but not under a last item that already shows its own row (then only the section's Details stays, or no row); opening or closing that item brings it back or hides it (`node --test --test-name-pattern='never stacks two action rows' test/design.test.mjs`). Disagree opens the comment box asking What is off?; Send saves it with `POST /api/annotations` (`{key, part, verdict?, text?}`, beside the design notes in `<board>.annotations.jsonl`) and the part shows Sent to the agent. The author agent's `wait --filer <id> --events` gets one `comment` event with the part and the words, once; the board then shows Agent read it, and `deeper <board> --filer <id> --id <comment id> --text …` puts the reply under it. Agree is one tap and saved at once. An answers-only board (the live one) shows and takes them all the same. Drive: `done-done run part-comment` (`part-comment-shots.mjs <out> light|dark 390|1280`, repeat per cell; `PART_COMMENT_BEFORE=1 SIGN_OFF_REPO=<base checkout>` records the page before). It asserts the five controls, their 44 px hit squares, the menu, What is off?, the saved line, the wait event, Agent read it and the reply, and the item row; light 390 also records `scroll-and-tap.mp4`. Contract proof with no browser: `node --test --test-name-pattern='comment on a report part' test/contract.test.mjs`.
- Go ahead sends the decisions as one structured answer (`answers --json`); the plan stays open and shows Sent.
- Active engagement listeners: report-only boards and sent plans keep `wait --filer <id> --events` open before a tap. Requests are filer-isolated and taken once, including concurrent listeners, queued requests, timeouts and server/listener restarts. Board-wide answer consumers cannot take them. This is not dormant-session wake-up.

- Standalone owner delivery (CLI-only): the packed package includes the generated skill. A real installed Claude Code author registers its actual UUID, exits, and resumes via the package-owned dispatcher on Go deeper. Local delivery records distinguish process handoff from explicit owner acknowledgement; inaccessible owners remain queued with the real error. Only Claude Code is supported, with one final atomic reply. No Firstmate dependency; older schemas retain the legacy Go deeper path.

## Drive

For all section presets, run `GUIDE_PRESETS=1 GUIDE_THEME=light GUIDE_WIDTH=390 done-done run guide`, then repeat dark/390, light/1280 and dark/1280. This extends the exact native-session Simplify proof below: every preset on plan 3/report 4, first custom text, question composer focus, follow-up, rapid same-part taps, idempotent HTTP retry, exact action/text/part in persisted owner requests, acknowledgement and completed answers from the original author UUID. All rendered parts must have the same controls. Every free-text box's placeholder is measured in the browser against the room inside the box (at most 80% of it, so it fails at 390 if a wider phone font would cut it off, as "Ask anything about this pa" was) and a `<kind>-freetext` shot is saved. The plan send-back notes remain intact. For the pre-change matrix use `GUIDE_BEFORE=1` with the same script on the base UI; paired plan-presets/report-presets screenshots use the same filenames. Run the default legacy journey too for Go ahead and old Go deeper. Inspect all captures and the sampled interaction recording. Native owner diagnostics bind every resumed UUID and request id; no scripted reply qualifies for presets.

For selected-text targets, run `done-done run selection` for each theme and width (`PLAN_REVIEW_DIAGNOSTICS` optional; the script is `selection-shots.mjs <output> light|dark 390|1280`). It posts a synthetic plan and report whose first understood line repeats `ask 🙂`, then drives the page: the second repeat by code-point offsets (UTF-16 would say 18), the third by real keyboard (`Shift+ArrowRight`, `Tab` into the tray, `Enter`), Ask a question with a quote, cancel by collapsing and by Escape, a selection across two fields and across two sections (no presets, nothing saved), a copy event the page does not cancel, at least 20px between the selection and the tray for the native handles, and a revised document that refuses the open page's request as stale with nothing saved. Its replies are a labelled stand-in (`deeper --filer`); the owner-wake proof stays with the real-owner journeys. Look at every tray, pending and answer capture. The server-side offsets, Unicode and refusals run in `node --test --test-name-pattern='a guided plan and report' test/contract.test.mjs`.

For the versioned Simplify loop, run `GUIDE_SIMPLIFY=1 GUIDE_THEME=light GUIDE_WIDTH=390 done-done run guide` and repeat dark/390, light/1280 and dark/1280. This opt-in hosted proof runs the installed authenticated Claude Code with its normal HOME: the real author revises and posts both synthetic examples, registers its actual UUID, exits, then resumes for each Simplify button. No scripted Simplify reply qualifies. It asserts author UUID = requested resume UUID = returned native UUID, no native error, explicit owner-read acknowledgement, matching request id/filer/revision, completed in-place text, unread across reload, seen only after visibility, and byte-identical documents/plan decisions. The extra conversation-only sentence is diagnostic, not a gate; the original slice-2 native test and its memory assertion remain unchanged. Before, pending and New screenshots cover both kinds; the light/390 cell also records timestamped sampled frames through chrome-devtools-axi into `simplify-sampled.mp4` (not full-frame-rate native video). Native owner stdout/stderr and target/answer JSON are saved in the sibling diagnostics folder. Look at every shot and sample the recording. New is persisted per answer piece, separately from section receipts. Queued delivery failures are visible, not substituted answers.

The existing guided CLI/server integration also exercises version-1 retry identity, distinct asks on one part, unknown/stale targets and selections, wrong-owner and stale replies, streaming, exact seen cursor and no decision mutation: `PATH=/usr/bin:$PATH node --test --test-name-pattern='every shipped fixture|a guided plan and report' test/contract.test.mjs`.

For owner registration/failure/idempotency, extend the built-CLI journey: `PATH=/usr/bin:$PATH node --test --test-name-pattern='standalone owner registration' test/contract.test.mjs` (put the native Node directory first where a version-manager shim needs HOME trust). It uses a private board/server, real missing-host failure, wrong-filer/owner rejection, explicit acknowledgement, repeated final reply and dispatcher restart.

For the real dormant-owner proof, set `SIGN_OFF_LIVE_OWNER=<absolute evidence folder>` and run `node --test --test-name-pattern='installed standalone Claude owner' test/contract.test.mjs` through the worker memory gate when required. This opt-in hosted-model journey uses the normal already-authenticated installed Claude Code (never copies credentials or changes its HOME), `claude-haiku-5-5`, npm pack/install in an empty project, and the packaged skill. It saves authentic argv/stdout/stderr in `installed-owner.log`. The owner authors and registers, then exits before the HTTP Go deeper tap. A missing executable queues a real failure; a new dispatcher process restores PATH and resumes the same UUID, explicitly acknowledges, and completes an explanation containing an ordinary fact retained only in that conversation. Assert the fact IN THE BOARD ANSWER, other-filer requests unread, and no duplicate text on dispatcher replay. A scripted reply or merely successful host launch does not qualify. Inspect the native result's `session_id` against the author UUID; no substitute host or Firstmate path is admitted. Keep the hosted journey opt-in for normal offline CI; run it explicitly for owner delivery changes. Non-visual: screen none, no screenshot matrix.

For a non-visual listener change, run `npm run build && node --test --test-name-pattern='engagement listeners|a guided plan and report|wait --events' test/contract.test.mjs`. This drives the real built CLI and a private server, checks the active-before-tap listener on report-only boards and sent plans, queues before waiting, races two same-filer listeners, restarts the server/listener, and preserves old answer/round events. No browser or model is needed for this delivery-only proof.

For a change to the skill's report or plan guidance (screen: none), run `done-done run research-bar` (`research-bar-shots.mjs`: clean install, the sample report and plan in `research-bar-sample/`, 16 shots, each scrolled to its part under a label bar naming the sample, the part, theme and width), then follow only the packaged skill from the clean install: write one research report and one plan from a real question with `report init`, post both on a throwaway board (HOME, XDG_* and SIGN_OFF_HOME in a temp folder), open `#reports/<key>` and `#waiting/<key>` at 390 and 1280 in light and dark, open every item, scroll the reader through and look at every screen. Check each point of the research bar by hand against what the board shows, and stop the board and browser.

For item detail and the comparison table, run `done-done run -- node .agents/skills/done-done-verify-sign-off/table-shots.mjs <report.json> <plan.json>` (an output folder as a third argument runs it outside done-done). It packs and installs the checkout in an empty folder with a throwaway HOME and XDG_*, posts the given research report and plan, serves them, and captures `report-compare`, `plan-lines` and `plan-risks` at 390 and 1280 in light and dark (12 shots). Each capture checks that nothing overflows and there are no console errors. It also measures that the table is a table at 1280 and stacked at 390, with every option and axis; that the opened item shows one line per point; and that the buttons of the item with no detail sit at least 8 px inside it. Name the parts with `TABLE_SECTION` (default `compare`), `LINES_ITEM` (`research:0`) and `BARE_ITEM` (`risks:1`). `TABLE_PART=compare`, `lines` or `padding` drives one part alone, so each run's `steps.json` names that one thing and the judge gets one-part claims; cite only that part's shots and its `<part>-measures.txt` (option columns and point rows; detail lines; buttons and their smallest inner gap in px). Results also go to `layout-checks.txt` and `post.txt`; the script stops its board and browser and removes its temp folder. Look at every shot. The page-level check is `node --test --test-name-pattern='item detail keeps its line breaks' test/design.test.mjs`.

For the visual guided-page journey, build with `npm run build`. Run `node .agents/skills/done-done-verify-sign-off/guide-shots.mjs "$DONE_DONE_EVIDENCE_ROOT" light 390` and repeat for dark/390, light/1280 and dark/1280, each in its own output folder (9 shots per cell). The same through done-done: `GUIDE_THEME=dark GUIDE_WIDTH=1280 done-done run guide`.
The script does the install, authoring, posting and serving, then drives the browser through chrome-devtools-axi: plan top, a part read (receipt), Details open, Go deeper answered, the decision, Sent, the agent's read receipt, then the report top and a Go deeper on the report. Each capture asserts no overflow, no console error and no failed request, and writes its claim and DOM record to the sibling diagnostics folder.
Go deeper is answered by `deeper-agent.mjs`, which waits as an agent does (`wait --filer … --events`) and streams the answer with the installed `deeper` command. With `MINIMAX_API_KEY` in the environment (set per command, from the file the owner keeps, never printed or saved) a model writes it from the document; without it a plainly labelled stand-in answers, which still proves the streaming and the receipts. A stand-in run is not proof of a model-written answer.
Look at every capture: the answer in place under its part, no cut text under the sticky bar, receipts with times, My pick on the recommended option only.

## Real-phone acceptance

Use the dedicated test phone only under its keeper lock and with serial-scoped adb. Start a new throwaway board with the installed packed CLI, never an existing personal board. For an authorized local adb-reverse lab, bind the server to 127.0.0.1, reverse only its port, and open its localhost URL with an explicit Chrome activity component. Verify `topResumedActivity` or `mCurrentFocus` identifies Chrome before every capture and between asks; CDP page creation alone does not prove the browser is visible. Never inspect personal tabs or apps. Delete an unexpected personal-screen capture and stop.

Drive one plan preset, its initial free-text ask, and a report preset through the page. Keep the original registered Claude UUID; inspect native dispatcher output to prove requested resume UUID = returned session_id, no native error, exact request ids, explicit owner-read and completed answers. Capture pending, then the expanded New answer. Keep a fresh answer offscreen through reload and prove New remains before revealing it; do not reset its seen cursor. Also force a missing-host delivery failure, restore the real route and prove the same request completes without duplicate text or document/decision changes. Use instant scrolling or wait for painted scroll settlement before capturing; an intermediate screen is not answer proof. Capture both phone themes and inspect every retained image.

For a native recording without a device output path, use `adb -s "$TEST_PHONE" exec-out screenrecord --output-format=h264 --time-limit 170 - > "$OUT/phone.h264"`, then `ffmpeg -f h264 -i "$OUT/phone.h264" -c copy "$OUT/phone.mp4"`. Check early that bytes arrive, enforce an outer deadline, verify the recorder actually exits, decode the complete MP4 and inspect cited frames. A zero-byte stream, a running process beyond its native limit, or a path/stop Permission denied is a failure, not recording proof. Stop only the exact recorder this drive started; do not overlap retries or touch pre-existing recorders. A screenshot sequence is not a video: use it instead only with an explicit recorded acceptance exception, naming the absent video, exact failure, actual capture times, request ids and remaining limitations. Remove task-owned forwarding, stop the browser/server, restore authorized device state and release the lock; disclose any owned process that cannot be stopped.

## Cleanup

The script stops its own browser session and server and prints its scratch folder (an `so-guide-*` folder in the temp dir); remove that folder after the run. Keep output evidence outside the repo.
Phone proof for selected text, on a real phone: post a plan and a report written by a real owner session (registered with `owner --filer`), serve the board on loopback and `adb reverse` the port, open Chrome with an explicit component, then long-press a word inside a paragraph with `input swipe x y x y 900`, drag a native handle, and tap a tray preset. Capture each step with `adb exec-out screencap -p`, crop away the status bar, browser bar and gesture bar, and check that the tray sits below the native handles and toolbar, the quote shows with the pending request, and a real owner's answer (`owner --dispatch`) lands under the part with the same quote. Never tap the native toolbar's Web search or Share; run it under the phone lock.
