# Tickets

Tickets are not kept on the board. The Tickets screens, `sign-off-axi ticket` and the board's `/api/tickets` routes read and write them only through the ticket adapter: one executable, named by `SIGN_OFF_TICKETS_ADAPTER`, called as `adapter <operation>` with one JSON request on stdin and one JSON response on stdout (`docs/ticket-adapter.md`). The board writes no ticket file and keeps no cache; every read is another call, and a failed call is shown as the adapter said it.

## Sub-features

- `ticket`: no flag lists every ticket (`--json` gives them as the adapter sent them, with the keys of the cards that name each); `--id` shows one with its cards; `--fields` prints the adapter's `describe`; `--create --set title=...`, `--id <id> --rev <rev> --set k=v --unset k`, `--history` and `--text <words>` write or read through the adapter. A write carries `--op-id` (the CLI makes one) so a repeat is safe. `--id <id> --comment '<json>'` still records a comment the person made in the fleet dashboard, in `<board>.ticket-comments.jsonl`.
- `--ticket <id>` on every way a card gets in (`raise`, `post`); it is a loose reference, never checked at post time. A card's screen shows a Ticket row with the id, which opens the ticket's page; the ticket's page lists the cards that name it.
- The Tickets screen (`#tickets`) is a board in the calm look the captain picked on 16 Nov (option 2): one column for each status the adapter lists (its own words and order, a status `describe` does not list after them, none for a status with no ticket), cards newest change first, each with the title, the ticket's own `id` in small monospace (a long hash id shortened in the middle on the card only) and who has it and when it changed; on a phone one column at a time with a tab for each (its mark and count, the name of the one in view). The board shows what the adapter lists and holds no word for a closed ticket. Its head has the filter drawn from the fields `describe` gives words for, New ticket, and links to **Epics** (`#epics`, tickets that others name as `parent`, one card each with the tickets under them and how they stand) and **Activity** (`#activity`, the `history` of the tickets that changed last, naming who made or moved each one and narrowing to one person with its Person pick; "This backend keeps no history." when `describe` lacks `history`).
- An epic's page (`#epics/<id>`): the epic, New ticket in this epic, and the tickets under it grouped by the status words the backend gave. A group of tickets is a ticket others name as `parent`, so a ticket under no epic sits in the No epic group and the board never guesses which `kind` means an epic.
- A ticket (`#ticket/<id>`) opens as a sheet over the board (from the foot on a phone, from the right edge on a desk): its whole id with a Copy button (it says Copied, and the clipboard holds exactly the id), the title, where it stands, its facts as `describe` names them, the body, every key of `extra` and every top-level key the board does not know under More fields, links, the tickets under it, the cards that name it, its history as a timeline and a comment box where the backend has `comment`. A ticket the list does not carry (a card names it) is read on its own and opens in the same sheet; one that cannot be read says so.
- New ticket (the round + in the header, `c` on a desk) and Edit are drawn from `describe`; an edit sends only the changed fields with the `rev` that was read. `invalid` marks the fields the adapter named and keeps every word typed; `conflict` shows the adapter's current version beside the person's ("Now", "Yours") with Save over theirs and Discard mine. There is no delete.
- A failed read shows the adapter's `code: message` with Retry and no rows. A list the adapter does not vouch for (`complete` not true) is `incomplete`, with no rows, never a partial list.
- Where a status, kind or label word comes from: the adapter. The board holds none.

## Drive

`node .agents/skills/done-done-verify-sign-off/tickets-board-shots.mjs <folder> <light|dark> <390|1440>` (journey `tickets-board`, one width and theme per run, or all four with none), after `npm run build`. It serves a throwaway board against the stand-in adapter holding thirteen tickets (short ids, one long hash id, an epic with three tickets under it, two people, three statuses the stand-in lists and one it does not) and captures the board, on a phone the third column's tab, a ticket's sheet with its whole id, Copy turned to Copied with the text read back from the clipboard, a ticket with history and More fields, a failed read and an incomplete list, one png each, with `steps.json`; it fails on a layout lint fault in any frame. `DEMO_PAGE=<the option-2 demo's html>` also captures the demo at the same size and theme and writes `side-board` and `side-sheet` frames with the demo on the left and the build on the right. Look at every capture: the column heads are the stand-in's own words, each card carries its id under the title (the long one shortened with an ellipsis in the middle), the sheet shows it whole, a failure reads `unavailable:` with the adapter's message and a Retry button and no cards.

`node .agents/skills/done-done-verify-sign-off/tickets-adapter-shots.mjs <folder> <light|dark> <390|1280>` (journey `tickets-adapter`, one width and theme per run), after `npm run build`. It serves a throwaway board against the stand-in adapter on its own Chromium at exact device metrics (390 is a 2x mobile emulation) and captures the list, a ticket with More fields, a conflict, a failure and an incomplete list, one png each, with `steps.json`. Look at every capture: the group headings are the stand-in's own words, a failure reads `unavailable:` with the adapter's message and a Retry button and no rows, and a conflict has both versions with the person's text still in the form.

`node .agents/skills/done-done-verify-sign-off/tickets-create-shots.mjs <folder> <light|dark> <390|1280>` (journey `tickets-create`, one width and theme per run) drives what a person makes and groups: the New ticket sheet whose fields, kinds and epic pick come from `describe`, a ticket made under an epic with the assignee it was given, the Epics view with each epic's count, one epic's page with New ticket in this epic, and Activity narrowed to one person. Its board, the stand-in adapter, says who did a write (`TICKET_STANDIN_ACTOR`), so the history names two people; the run fails on a layout lint fault in any frame. Look at every capture: the kinds read as the backend's own words, an epic's head carries its title and how many are under it, and the Activity pick leaves only that person's events.

Tests: `test/tickets.test.mjs` (the CLI and the API against the stand-in: an unknown field, a conflict, a failure, `incomplete`, no ticket file, a patch rather than a rewrite) and `test/ticket-adapter.test.mjs` (the interface itself).
